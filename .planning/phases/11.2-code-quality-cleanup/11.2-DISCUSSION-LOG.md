# Phase 11.2 — Discussion Log

**Date:** 2026-06-16
**Format:** Initial context gathered from user direction. Updated session adds three decisions.

## Areas Discussed (initial session)

### 1. IP Validation mechanism
**User's direction:** Remove `IpValidation` object; use Ktor's `RequestValidation` plugin via a new `AddZoneRequest` body model instead of path parameter.
**Decision:** `IpValidation.kt` deleted; `AddZoneRequest(ip: String)` added; `validate<AddZoneRequest>` registered in `RequestValidationConfig.kt`.

### 2. Service nesting / splitting
**User's direction:** "Za dużo wcięć i ciężko czyta się kod" — NetworkDiscoveryService, SchedulerService, ScreenDriverService, WebhookService all need nesting reduced and large methods split into smaller private functions.
**Decision:** Private extraction per service; no logic change, only structural cleanup.

### 3. ZoneRegistry hardcoded string types
**User's direction:** "Zahardkodowane typy configów" — `"MAX7219"`, `"LCD"`, `"OLED"` string literals should use `DisplayType` enum.
**Decision:** `DisplayType.fromString()` used in `initLocalZone`; `ZoneConfig.type` aligned to enum.

### 4. DisplayRoutes enum + RequestValidation
**User's direction:** POST `/select` has too much logic; hardcoded type strings; should use RequestValidation; proper response handling.
**Decision:** `validate<DisplaySelectRequest>` added to plugin; route handler simplified to receive → call service → respond.

### 5. History routes / repository separation
**User's direction:** "historyUIRoutes nie powinno bezpośrednio wołać repository, w ogóle routes i controllery nie powinny wołać bezpośrednio do repository".
**Decision:** New `HistoryService` wraps `HistoryRepository`; both `historyRoutes` and `historyUIRoutes` receive `HistoryService`.

### 6. DisplayConfig enum
**User's direction:** `display config powinien użyć enum zamiast string`.
**Decision:** `DisplayConfig.type: DisplayType` instead of `String`.
