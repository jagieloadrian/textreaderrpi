# Phase 11.2: Code Quality Cleanup - Context

**Gathered:** 2026-06-16
**Status:** Ready for planning

<domain>
## Phase Boundary

Service classes (`NetworkDiscoveryService`, `SchedulerService`, `ScreenDriverService`, `WebhookService`, `ZoneRegistry`) are refactored for flat nesting and smaller functions. Hardcoded string literals for display types are replaced by `DisplayType` enum throughout. Route handlers (`historyUIRoutes`, `historyRoutes`, `DisplayRoutes`, `ZoneRoutes`) are cleaned of logic and direct repository calls. A new `HistoryService` mediates between routes and `HistoryRepository`. IP validation moves from a static `IpValidation` object into the Ktor `RequestValidation` plugin via a new `AddZoneRequest` body model.

No new features. No schema changes. No new endpoints. This phase is pure code quality.

**Prerequisite:** Stage and commit all current working-tree changes (Duration.milliseconds conversions, HistoryRepository expression form, LcdDisplay/OledDisplay init inlining) as a `fix(11)` commit before phase 11.2 execution begins (D-23).

</domain>

<decisions>
## Implementation Decisions

### IP Validation
- **D-01:** Delete `IpValidation` object (`src/main/kotlin/com/anjo/validation/IpValidation.kt`)
- **D-02:** Add `AddZoneRequest(ip: String)` data class in `src/main/kotlin/com/anjo/model/`
- **D-03:** Add a `validate<AddZoneRequest>` block to `RequestValidationConfig.kt` — use the same RFC1918 logic currently in `IpValidation.isValidPrivateIpv4`
- **D-04:** `ZoneRoutes` POST `/{ip}` becomes `POST /` (body), `call.receive<AddZoneRequest>()` — Ktor's `RequestValidation` plugin throws `RequestValidationException` on invalid IP, which produces a 400 automatically; no manual `if` in the route handler

### DisplayType enum enforcement
- **D-05:** `DisplayConfig.type` changes from `String` to `DisplayType` (`src/main/kotlin/com/anjo/config/model/DisplayConfig.kt`). Default value becomes `DisplayType.MAX7219`
- **D-06:** `ZoneRegistry.initLocalZone` uses `DisplayType.fromString(zoneConfig.type.name)` / `when (displayType)` with enum cases instead of string literals `"MAX7219"`, `"LCD"`, `"OLED"`
- **D-07:** `ZoneConfig.type` also switches from `String` to `DisplayType` (`src/main/kotlin/com/anjo/config/model/ZonesConfig.kt`)
- **D-22 ConfigLoader enum conversion:** When `DisplayConfig.type` and `ZoneConfig.type` change to `DisplayType`, `ConfigLoader` must call `DisplayType.fromString(config.propertyOrNull("...").getString() ?: "MAX7219")` for both fields. If `fromString` returns `DisplayType.UNKNOWN` (unrecognized value in YAML), log a warning and substitute `DisplayType.MAX7219`. `ConfigLoader.kt` is a file to update. No automatic deserializer handles this — it is manual parsing via Ktor config API.

### DisplayRoutes POST /select cleanup
- **D-08:** Add `DisplaySelectRequest.type` validation via `RequestValidation` plugin — add `validate<DisplaySelectRequest>` in `RequestValidationConfig.kt` checking `DisplayType.fromString(req.type) != DisplayType.UNKNOWN`. `DisplaySelectRequest.type` stays `String` (consistent with `AddZoneRequest.ip` pattern; all validation through the plugin, not deserialization).
- **D-09:** Remove the `val allowed = setOf(...)` + `if (normalized !in allowed)` block from `DisplayRoutes`. Route handler body becomes: receive → queueDisplaySwitch → respond. No branching for type validation inside the route
- **D-10:** Use `DisplayType.fromString(request.type)` in `ScreenDriverService.queueDisplaySwitch` if needed; the validation has already passed by the time the handler calls the service

### HistoryService (new service layer)
- **D-11:** Create `HistoryService` in `src/main/kotlin/com/anjo/service/HistoryService.kt` — wraps `HistoryRepository`, exposes `findPaginated(page, size, effect, source)` and any other query methods used by routes
- **D-12:** `historyUIRoutes` receives `HistoryService` instead of `HistoryRepository` — no `import com.anjo.db.HistoryRepository` in route files
- **D-13:** `historyRoutes` (API) receives `HistoryService` instead of `HistoryRepository` — same rule
- **D-14:** Wire `HistoryService` in `DependencyInjection.kt` — it receives `HistoryRepository` from DI

### Service method nesting reductions
- **D-15 NetworkDiscoveryService:** Extract `startMdnsListener()` private fun from `start()`. Extract `buildNetworkZone(ip, method, name, type)` private fun to remove duplication between `onDeviceDiscovered` and `parseDiscoveryReply`. The nested `scope.launch { ... addServiceListener { ... scope.launch { } } }` collapses to two flat calls
- **D-16 SchedulerService:** Extract `checkExpiry(schedule): Boolean` and `checkMaxRuns(runs, schedule): Boolean` private funs from `launchRecurring`. The nested `if (expiresAt != null) { try { ... } catch { ... } }` inside `while` body becomes a single `if (checkExpiry(schedule)) break`
- **D-17 ScreenDriverService:** Extract `withMutex(mutex, alreadyLocked, block)` suspend fun that handles the `if (alreadyLocked) block() else mutex.withLock { block() }` pattern — used in both `renderImmediate` and `runScheduledRender`. Also extract `acquireMutex(zoneId, policy): Mutex?` to unify the tryLock / getOrPut logic in `displayImmediate` and `displayScheduled`
- **D-18 WebhookService:** `send()` is already small; extract `executePost(url, payload)` suspend fun that contains the `withTimeout` + post call — leaves `send()` as a clean fire-and-forget launcher

### Prerequisite commit
- **D-23:** Before phase 11.2 execution, commit the current working-tree changes as `fix(11): duration-api + minor cleanup`. These include: `Duration.milliseconds` conversions in `RetryPolicy`, `EffectRenderer`, `LcdDisplay`, `OledDisplay`, `Max7219Matrix`, `SchedulerService`, `WebhookService`; `HistoryRepository` if-expression simplification; `LcdDisplay`/`OledDisplay` init-to-field-init refactor. These are phase 11 post-UAT cleanup, not part of 11.2.

### General rules (from user)
- **D-19:** No comments added to refactored code (project-wide coding rule)
- **D-20:** Validation logic stays in `ScheduleValidators` / `RequestValidators` / `RequestValidationConfig` — never in route handlers
- **D-21:** No `if`-chains in route handlers — use the plugin mechanisms

### Claude's Discretion
- Whether to rename `POST /zones/{ip}` to `POST /zones` or keep a different path — route shape is open as long as the IP comes from the body
- Method naming for extracted private functions — follow existing naming conventions in each file
- Whether `HistoryService` interface/class — class is fine (no need to extract an interface unless tests require it)

</decisions>
