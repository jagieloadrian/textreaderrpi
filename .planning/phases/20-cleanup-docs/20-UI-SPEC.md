### Table conventions (must match existing README patterns exactly — do not introduce a new table style)

| Table type | Header row |
|---|---|
| API endpoint table | `| Method | Path | Description |` — Method and Path both in backticks |
| Config/env-var table | `| Variable | Default | Description |` |
| Toolchain table | `| Tool | Version | Install |` |
| Troubleshooting table | `| Symptom | Cause / check |` |

### Code-block conventions

- Every fenced block is language-tagged: ```bash for shell/curl/wscat, ```c for Pico config, ```cpp or ```c for ESP32 config where applicable, ```kotlin for the one existing Gradle snippet, ```text for the Code Layout tree.
- `#` comments inside ```bash examples are allowed and expected (documentation convention, not a source file — does not conflict with the project's "no comments in code files" rule, which governs `src/`).
- One command (or one logical command+output pair) per fenced block where the existing README already does this — do not merge unrelated commands into one block.

### Table of Contents format

Flat GitHub-anchor bullet list directly under the title, before the first `---`:
```

- [Firmware](#firmware)
- [Configuration](#configuration)
- [Build and Run](#build-and-run)
- [Deployment](#deployment)
- [Code Layout](#code-layout)
- [Notes](#notes)
```
(Discretion item per CONTEXT.md — this flat, unindented form is the declared default; do not add sub-bullets beyond this unless a section review finds the flat list insufficient for scanning.)

## Copywriting Contract

The template's UI copy roles (CTA button, empty state, error state, destructive-confirmation dialog) describe interactive application chrome. This phase produces no interactive UI, so each role below is mapped to its nearest documentation equivalent — N/A is used only where genuinely no equivalent exists.

| Element | Copy |
|---------|------|
| Primary CTA | N/A — no buttons/dialogs. Nearest equivalent: the first command a new reader runs is `./gradlew run` (already documented under Build and Run) — no change needed, do not add a redundant "Quick Start" section per D-11's "keep section ordering tight" |
| Empty state heading/body | N/A — no application empty state exists in this phase's surface |
| Error state | Applies to the Firmware Troubleshooting table only: each row is phrased as **Symptom → Cause/check**, imperative and specific (e.g. "Board not detected over USB" → "Pico: check BOOTSEL mode entry; ESP32: check `idf.py -p /dev/ttyUSB0` port permission (`dialout` group on Linux)") — no vague "try again" phrasing |
| Destructive confirmation | Two destructive actions in this phase, both git-committed repo operations with no interactive UI, so "confirmation" means **commit-message clarity**, not a dialog: (1) `docs/` deletion — commit message must state salvage was completed and git history is the archive; (2) phase dirs 14–19 deletion — commit message must state git history preserves all planning artifacts, per D-06/D-07. Phase 20's own directory deletion is explicitly a separate, later, documented commit (D-07) — never bundled into the same commit as 14–19 |

### Tone

- Terse, technical, imperative for commands; declarative for descriptions — matches the existing README's established voice exactly (verified by reading the full current `README.md`). No marketing language, no exclamation points, no "simply"/"just"/"easily" hedge words.
- Firmware walkthrough written as "a complete beginner path on Linux" per CONTEXT.md specifics — each step is a runnable command or a concrete wiring fact, never a vague instruction.
- Facts must be code-verified, not copied from stale `docs/`/REQUIREMENTS.md prose (D-02, and the RESEARCH.md Pitfall 1 correction: ESP32 firmware is ESP-IDF/CMake, never write or imply "PlatformIO"/"platformio.ini" anywhere in the README).
- Deferred v1.3 items (OTA-as-finished, GIN index, multi-replica, Ingress/TLS-as-ready, "WebSocket live feed" phrasing for `/ws/zone/{id}`) must not appear worded as shipped v1.2 features — match the firmware README's own hedged OTA wording rather than overclaiming.
