<objective>
Close the two runtime blockers from 18-VERIFICATION.md (gaps CR-02 and CR-03). Both are Kubernetes API semantics defects in Helm templates that `helm lint`/`helm template` cannot catch: `privileged: true` placed at pod-level securityContext (silently ignored by Kubernetes, so hardware mode never gets device access), and a ServiceAccount name mismatch (`<fullname>-sa` created vs `<fullname>` referenced) that makes pod admission fail on any real cluster.

Scope is exactly these two fixes. Do not restructure the chart, do not touch _helpers.tpl (the `textreaderrpi.serviceAccountName` helper is correct and already used by the Deployment — the other two templates must converge on it).
</objective>

<acceptance_criteria>
1. `helm template textreaderrpi .devops/helm/textreaderrpi/ --set hardwareAccess.enabled=true` renders `privileged: true` under `spec.template.spec.containers[0].securityContext` and renders NO `securityContext` under `spec.template.spec`.
2. `helm template textreaderrpi .devops/helm/textreaderrpi/` renders the same name for: ServiceAccount `metadata.name`, Deployment `spec.template.spec.serviceAccountName`, and RoleBinding `subjects[0].name`.
3. `helm lint .devops/helm/textreaderrpi/` passes with 0 failures.
4. `helm template` renders without errors for both `hardwareAccess.enabled=true` and `=false`.
</acceptance_criteria>

<tasks>

### Task 1: Move privileged securityContext from pod level to container level

**File:** `.devops/helm/textreaderrpi/templates/deployment.yaml`

Remove this block from pod level (currently directly under `spec.template.spec`, before `containers:`):

```yaml
      {{- if .Values.hardwareAccess.enabled }}
      securityContext:
        privileged: true
      {{- end }}
```

Add the equivalent block inside the `textreaderrpi` container entry (sibling of `image:`, `ports:`, `envFrom:`), with container-level indentation:

```yaml
        {{- if .Values.hardwareAccess.enabled }}
        securityContext:
          privileged: true
        {{- end }}
```

**Verify:**
```bash
helm template textreaderrpi .devops/helm/textreaderrpi/ --set hardwareAccess.enabled=true
```
`privileged: true` appears only under the container's securityContext. With `--set hardwareAccess.enabled=false`, no securityContext renders at all.

**Commit:** `fix(18-09): move privileged securityContext to container level`

### Task 2: Unify ServiceAccount naming through the serviceAccountName helper

**Files:** `.devops/helm/textreaderrpi/templates/serviceaccount.yaml`, `.devops/helm/textreaderrpi/templates/rolebinding.yaml`

In `serviceaccount.yaml`, replace:
```yaml
  name: {{ include "textreaderrpi.fullname" . }}-sa
```
with:
```yaml
  name: {{ include "textreaderrpi.serviceAccountName" . }}
```

In `rolebinding.yaml`, replace the subject:
```yaml
    name: {{ include "textreaderrpi.fullname" . }}-sa
```
with:
```yaml
    name: {{ include "textreaderrpi.serviceAccountName" . }}
```

Do NOT modify `_helpers.tpl` or `deployment.yaml` — they already use the helper.

**Verify:**
```bash
helm template textreaderrpi .devops/helm/textreaderrpi/ | grep -E "serviceAccountName:|name: textreaderrpi" 
```
ServiceAccount name, Deployment serviceAccountName, and RoleBinding subject all render identically (e.g., `textreaderrpi`).

**Commit:** `fix(18-09): unify ServiceAccount name via serviceAccountName helper`
