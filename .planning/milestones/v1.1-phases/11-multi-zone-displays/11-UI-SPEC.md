# Phase 11 — UI Design Contract

> Visual and interaction contract for Phase 11: Multi-Zone Displays.
> Generated by gsd-ui-researcher. Verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | PicoCSS v2 (CDN) |
| Icon library | none (text labels only) |
| Font | system-ui (PicoCSS default) |

**Rationale (source: codebase scan):** The project is a Kotlin/Ktor server rendering HTML via `kotlinx.html`. `BaseLayout.kt` loads `https://cdn.jsdelivr.net/npm/@picocss/pico@2/css/pico.min.css` via CDN. No Tailwind, no shadcn, no React. This phase must extend the existing PicoCSS dark-theme pattern. The Material 3 full refresh is deferred to Phase 13 (REQUIREMENTS.md §UI-01).

**No shadcn gate applies.** This is not a React/Next.js/Vite project.

---

## Scope

Phase 11 adds the following UI surface:

1. **`BaseLayout.kt` nav update** — add a "Zones" link pointing to `/zones` between "History" and "Settings" in the top nav.
2. **`/zones` page** (`ZonesPage.kt`) — lists all registered zones (local + network) with status badges, plus two action forms:
   - "Scan for Displays" button (calls `POST /api/v1/zones/discover`)
   - "Add by IP" inline form (calls `POST /api/v1/zones/{ip}`, ZONE-06)

These are the only HTML-rendered UI changes in this phase. The `GET /api/v1/zones` JSON endpoint has no UI of its own.

## Color

PicoCSS v2 dark theme is active (`data-theme="dark"` on `<html>`). All colors must use PicoCSS CSS custom properties — no hardcoded hex values.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--pico-background-color` (approx #11191f) | Page background, main canvas |
| Secondary (30%) | `--pico-card-background-color` (approx #1c2732) | Zone cards, form containers |
| Accent (10%) | `--pico-primary` (approx #1095c1) | ONLINE badge background, "Scan" button, "Add" button |
| Destructive | `--pico-color-red-500` (approx #e53e3e) | OFFLINE badge background only |

**Accent reserved for:** ONLINE status badge, primary action buttons ("Scan for Displays", "Add Zone").

**Status badge palette:**
- ONLINE → PicoCSS `--pico-primary` background, white text
- OFFLINE → PicoCSS `--pico-color-red-500` (or `color: var(--pico-color-red)`) background, white text
- DEGRADED → PicoCSS `--pico-color-orange-500` background, white text

No hardcoded hex. All must be PicoCSS variables to remain theme-compatible with the Phase 13 Material 3 migration.

## Component Inventory

### 1. Nav Link (BaseLayout.kt change)

Add to the existing `<ul>` in `BaseLayout.render()`:

```
li { a(href = "/zones") { attributes["aria-current"] = if (activePath == "/zones") "page" else ""; +"Zones" } }
```

Position: after the "History" link, before the "Settings" link.

### 2. Zone Card (ZonesPage.kt)

Each zone renders as a PicoCSS `<article>` element:
- Header row: zone ID (bold), zone type (label), status badge (inline `<mark>`)
- Body: IP address (network zones only), discovery method (MANUAL / UDP / MDNS), last seen timestamp
- No action buttons on individual zone cards in Phase 11 (delete/manage deferred to Phase 13)

### 3. Status Badge

Rendered as `<mark>` with inline `style` attribute (PicoCSS `<mark>` carries background-color):
- ONLINE: `<mark style="background: var(--pico-primary)">ONLINE</mark>`
- OFFLINE: `<mark style="background: var(--pico-color-red-500, #c0392b); color: white">OFFLINE</mark>`
- DEGRADED: `<mark style="background: var(--pico-color-orange-500, #e67e22); color: white">DEGRADED</mark>`

### 4. "Scan for Displays" Button

A plain `<button>` (PicoCSS primary style) below the zone list:
- Label: "Scan for Displays"
- Triggers JavaScript `fetch("POST /api/v1/zones/discover")` via `app.js`
- On success: reloads the `/zones` page to reflect newly found zones
- Placed in its own `<section>` below the zone list

### 5. "Add by IP" Form

A PicoCSS `<form>` with:
- `<input type="text" placeholder="192.168.x.x" name="ip">` — IP address field
- `<button type="submit">Add Zone</button>` — submits via JavaScript `fetch` to `POST /api/v1/zones/{ip}`
- On success: reloads the `/zones` page
- Placed below the "Scan for Displays" section

## Interaction States

All interactions use inline JavaScript in `app.js` (no framework). Each async action follows the pattern established by existing pages:

| Trigger | Action | Success State | Error State |
|---------|--------|---------------|-------------|
| "Scan for Displays" click | `POST /api/v1/zones/discover` | Reload `/zones` with newly discovered zones appearing in list | Show inline error text below button |
| "Add Zone" form submit | `POST /api/v1/zones/{ip}` | Reload `/zones` with new zone visible | Show validation error inline (invalid IP or zone already registered) |
| Page load | `GET /zones` (server-rendered) | Zone list rendered | N/A — error handled by server |

**Busy state:** While scan is in-progress (up to 3 seconds per D-23), disable the "Scan for Displays" button and replace its label with "Scanning..." using JavaScript. Re-enable on completion.

## Implementation Notes for Executor

1. **New file:** `src/main/kotlin/com/anjo/web/templates/ZonesPage.kt` — follow `SchedulePage.kt` pattern (top-level `FlowContent.() -> Unit` extension function `zonesPage(zones: List<ZoneInfo>)`).

2. **New route file:** `src/main/kotlin/com/anjo/routing/ui/ZonesUIRoutes.kt` — follow `HistoryUIRoutes.kt` pattern (inject `ZoneRegistry` or a `ZoneRepository`, call `BaseLayout.render(pageTitle = "Zones — TextReaderRpi", activePath = "/zones") { zonesPage(zones) }`).

3. **BaseLayout change:** Add "Zones" nav link between "History" and "Settings" per the nav contract above. STATE.md decision: "add headExtra to BaseLayout before any page-specific CSS" — no additional CSS injection needed in this phase.

4. **`app.js` additions:** Two new async handlers:
   - `document.getElementById("scanBtn")` click → `fetch("/api/v1/zones/discover", { method: "POST" })` → reload or inject result
   - `document.getElementById("addZoneForm")` submit → `fetch("/api/v1/zones/" + ip, { method: "POST" })` → reload or inject result

5. **`ZoneInfo` view model:** The page template receives a list of view model objects (not raw DB rows) containing: `id`, `type`, `isLocal`, `ipAddress?`, `status`, `discoveryMethod?`, `lastSeenAt?`. The executor must define this view model in the routing layer.

6. **No inline `style` attributes** except for status badge colors (which require dynamic color selection not expressible in PicoCSS class alone). All other layout uses PicoCSS semantic elements (`article`, `section`, `form`, `button`, `mark`).
