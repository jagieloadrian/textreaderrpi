## Summary

Phase 11.2 is a pure refactoring pass — no new features, no schema changes, no new endpoints. All decisions are locked in CONTEXT.md. The research task is to map the exact current state of each affected file, identify every place a locked decision touches the codebase (including tests), and surface pitfalls that would cause the planner to produce broken tasks.

The three main work clusters are: (1) IP validation migration — delete `IpValidation`, create `AddZoneRequest`, extend `RequestValidationConfig`, change the route signature; (2) DisplayType enum propagation — change two config model fields from `String` to `DisplayType`, update `ConfigLoader` to call `fromString()`, replace string literal `when`-branches in `ZoneRegistry`; (3) service layer introduction — create `HistoryService`, re-wire `historyRoutes`/`historyUIRoutes`/`Routing.kt`/`DependencyInjection.kt`, and update tests that currently resolve `HistoryRepository` from DI. A fourth cluster — extracting private helper functions from four service classes — is mechanical but has test implications for `SchedulerService` and `ScreenDriverService`.

**Primary recommendation:** Work in discrete, buildable steps. Each step must produce a green test suite. The most dangerous single change is the `POST /zones/{ip}` → `POST /zones` (body) route flip, because five existing tests in `ZoneRoutesTest` call `client.post("/api/v1/zones/$ip")` and will need to be rewritten to `client.post("/api/v1/zones") { setBody(...) }` before the old route handler is removed.

### Pattern 1: RequestValidation extension — new validate block

**What:** Add a new `validate<T>` block inside the existing `install(RequestValidation) {}` lambda.

**When to use:** Any new body model that needs server-side validation before the route handler executes.

```kotlin
// Source: existing RequestValidationConfig.kt pattern in this project
install(RequestValidation) {
    validate<TextRequest> { textRequest ->
        RequestValidators.validateTextRequest(textRequest, apiConfig)
    }
    validate<Schedule> { schedule ->
        ScheduleValidators.validateSchedule(schedule)
    }
    validate<AddZoneRequest> { req ->
        RequestValidators.validateAddZoneRequest(req)
    }
    validate<DisplaySelectRequest> { req ->
        RequestValidators.validateDisplaySelectRequest(req)
    }
}
```

The validator function belongs in `RequestValidators.kt` as a top-level or object function, following the `ScheduleValidators` pattern. It returns `ValidationResult.Valid` or `ValidationResult.Invalid(message)`.

### Pattern 2: Enum field default in config model

**What:** Change `type: String = "MAX7219"` to `type: DisplayType = DisplayType.MAX7219` in data classes.

**When to use:** When the field can only hold one of a finite set of values that already has an enum representation.

```kotlin
// Source: com.anjo.model.DisplayType (existing in project)
data class ZoneConfig(
    val id: String,
    val type: DisplayType = DisplayType.MAX7219,
    val numDevices: Int = 2,
    val bus: Int = 0,
    val chipSelect: Int = 0
)
```

Callers that previously set `type = "MAX7219"` must be updated to `type = DisplayType.MAX7219`.

### Pattern 3: ConfigLoader — explicit fromString() conversion

**What:** `ConfigLoader` uses the Ktor config API directly (not Jackson/kotlinx-serialization), so there is no automatic enum deserializer. The getString() result must be converted manually.

```kotlin
// Source: existing ConfigLoader.kt manual parse pattern in this project
val type = DisplayType.fromString(
    config.propertyOrNull("display.zones.$index.type")?.getString() ?: "MAX7219"
)
if (type == DisplayType.UNKNOWN) {
    log.warn("Unknown display type for zone index $index; defaulting to MAX7219")
}
val safeType = if (type == DisplayType.UNKNOWN) DisplayType.MAX7219 else type
zones.add(ZoneConfig(id = id, type = safeType, ...))
```

This pattern must be applied to both `display.type` (for `DisplayConfig`) and `display.zones.$index.type` (for `ZoneConfig`) plus the fallback branch.

### Pattern 4: when (displayType) with enum cases

**What:** Replace `when (zoneConfig.type.uppercase()) { "MAX7219" -> ... }` with `when (zoneConfig.type) { DisplayType.MAX7219 -> ... }` after the field is `DisplayType`.

```kotlin
// Source: ZoneRegistry.initLocalZone — before and after
// Before:
when (zoneConfig.type.uppercase()) {
    "MAX7219" -> Max7219Matrix(...)
    "LCD" -> LcdDisplay(ctx)
    "OLED" -> OledDisplay(ctx)
    else -> { log.warn(...); OfflineDisplayDriver }
}

// After (D-06):
when (zoneConfig.type) {
    DisplayType.MAX7219 -> Max7219Matrix(...)
    DisplayType.LCD -> LcdDisplay(ctx)
    DisplayType.OLED -> OledDisplay(ctx)
    DisplayType.UNKNOWN -> { log.warn(...); OfflineDisplayDriver }
}
```

The `else` branch becomes an explicit `DisplayType.UNKNOWN` case. The Kotlin compiler enforces exhaustiveness on `when` over an enum, which catches missing cases at compile time.

### Pattern 5: HistoryService delegation wrapper

**What:** A thin class that delegates all calls to `HistoryRepository`. No business logic other than forwarding.

```kotlin
// Source: D-11 from CONTEXT.md — derived from ScheduleValidators/RequestValidators delegation pattern
class HistoryService(private val repository: HistoryRepository) {
    suspend fun findPaginated(
        page: Int,
        size: Int,
        effect: String? = null,
        source: String? = null
    ): Pair<List<HistoryRecord>, Long> = repository.findPaginated(page, size, effect, source)
}
```

Route handlers replace `historyRepository.findPaginated(...)` with `historyService.findPaginated(...)`. Import of `HistoryRepository` is removed from route files.

### Pattern 6: Extracted private suspend fun — mutex helper

**What:** Extract the repeated `if (alreadyLocked) block() else mutex.withLock { block() }` pattern from `ScreenDriverService.renderImmediate` and `runScheduledRender` into a shared private inline function.

```kotlin
// Source: ScreenDriverService — D-17 extraction target
private suspend fun withMutex(mutex: Mutex, alreadyLocked: Boolean, block: suspend () -> Unit) {
    if (alreadyLocked) {
        block()
    } else {
        mutex.withLock { block() }
    }
}
```

Both `renderImmediate` and `runScheduledRender` call this instead of duplicating the branching.

### Anti-Patterns to Avoid

- **Route handler validation:** Any `if (normalized !in allowed)` or `if (!IpValidation.isValidPrivateIpv4(ip))` block inside a route handler body. Move to `RequestValidators` and register via plugin.
- **String literal dispatch:** `when (zoneConfig.type.uppercase()) { "MAX7219" -> ... }`. Replace with enum when the field becomes `DisplayType`.
- **Direct repository import in route files:** `import com.anjo.db.HistoryRepository` in `HistoryRoutes.kt` or `HistoryUIRoutes.kt`. After the change only `HistoryService` is imported.
- **Comments in refactored code:** The project rule prohibits all inline `//`, block `/* */`, and KDoc. The existing `RequestValidators.kt` has three inline comments that must be removed as part of this phase (they are in the file being edited).
- **Forgetting NetworkZone.type field:** `com.anjo.model.NetworkZone.type` is `String` and is NOT in scope for the enum change (it represents data from the DB column, which stays `varchar`). The enum change only applies to `DisplayConfig.type`, `ZoneConfig.type`, and the `ConfigLoader` parsing logic.

## Common Pitfalls

### Pitfall 1: Status code mismatch — tests expect 400, plugin produces 422

**What goes wrong:** Five tests in `ZoneRoutesTest` and one in `WebAndDisplayRoutesTest` currently assert `HttpStatusCode.BadRequest` (400) for invalid IP / invalid display type. After the validation moves to the `RequestValidation` plugin, `ErrorHandling.kt` maps `RequestValidationException` to `422 Unprocessable Entity`. The tests will fail.

**Why it happens:** The old route handlers called `call.respond(HttpStatusCode.BadRequest, ...)` manually. The plugin does not — it throws `RequestValidationException`, which `configureErrorHandling()` catches and maps to 422.

**How to avoid:** Update the affected test assertions from `HttpStatusCode.BadRequest` to `HttpStatusCode.UnprocessableEntity` and remove the `bodyAsText() shouldContain "Unsupported driver type"` assertion (or align the error message with whatever the validator puts in `ValidationResult.Invalid("...")`).

**Affected tests:**
- `ZoneRoutesTest`: "POST /api/v1/zones/{ip} with a public IP returns 400" — becomes 422
- `ZoneRoutesTest`: "POST /api/v1/zones/{ip} with an invalid IP format returns 400" — becomes 422
- `WebAndDisplayRoutesTest`: "should reject invalid driver type with 400 on POST /api/v1/display/select" — becomes 422; body assertion must match the validator message string

### Pitfall 2: Route path change breaks ZoneRoutesTest call sites

**What goes wrong:** The five `ZoneRoutesTest` tests that call `client.post("/api/v1/zones/192.168.1.50")` or `client.post("/api/v1/zones/8.8.8.8")` use the path-parameter form. After D-04, the route becomes `POST /api/v1/zones` with the IP in the body. All these tests must be rewritten.

**Why it happens:** The old route was `post("/{ip}")`. The new route is `post("/")` with `call.receive<AddZoneRequest>()`.

**How to avoid:** When updating `ZoneRoutes.kt`, also update all `ZoneRoutesTest` call sites to:
```kotlin
client.post("/api/v1/zones") {
    header(HttpHeaders.ContentType, ContentType.Application.Json.toString())
    setBody("""{"ip":"192.168.1.50"}""")
}
```

### Pitfall 3: HistoryRoutesTest and HistoryUIRoutesTest resolve HistoryRepository from DI — must stay resolvable

**What goes wrong:** `HistoryRoutesTest` and `HistoryUIRoutesTest` do:
```kotlin
application.dependencies.getBlocking<HistoryRepository>(DependencyKey<HistoryRepository>())
```
to seed test data. `HistoryRepository` must remain registered in `DependencyInjection.kt` even after `HistoryService` is added, because tests use it directly via `getBlocking<HistoryRepository>()`.

**Why it happens:** The DI binding for `HistoryRepository` must not be removed when `HistoryService` is added. `HistoryService` itself receives `HistoryRepository` from DI.

**How to avoid:** In `DependencyInjection.kt`, add `provide { historyService }` without removing `provide { historyRepository }`. The `ApplicationTest` smoke test also checks `getBlocking<HistoryRepository>()` — it must still pass.

Additionally, the `ApplicationTest` will need to add a `getBlocking<HistoryService>` assertion once `HistoryService` is registered. [ASSUMED — based on existing smoke test pattern; confirm whether this assertion should be added]

### Pitfall 4: Comments in RequestValidators.kt must be removed

**What goes wrong:** `RequestValidators.kt` currently contains three inline comments (`// Check for blank text`, `// Check length against configured max`, `// All validations passed`). When this file is edited to add `validateAddZoneRequest`, those existing comments violate the project no-comments rule.

**Why it happens:** The file predates the rule enforcement discovered in phase 7.

**How to avoid:** Remove all three inline comments from `RequestValidators.kt` as part of the edit that adds `validateAddZoneRequest`.

### Pitfall 5: ZoneRegistry.initLocalZone — `zoneConfig.type` used as String in LocalZoneDriver constructor

**What goes wrong:** After `ZoneConfig.type` becomes `DisplayType`, the call `LocalZoneDriver(id = zoneConfig.id, type = zoneConfig.type, driver = driver)` passes a `DisplayType` where `LocalZoneDriver.type: String` is expected. The `NetworkZoneDriver` also takes `type: String`.

**Why it happens:** `LocalZoneDriver` and `NetworkZoneDriver` both hold `type: String` because it maps from the DB (`network_zones.type varchar`). These zone driver constructors are not in scope for the enum change.

**How to avoid:** At the call site in `ZoneRegistry.initLocalZone`, pass `zoneConfig.type.name` to convert `DisplayType` back to its `String` name. Same for any other call site that passes `ZoneConfig.type` into a `String`-expecting parameter.

### Pitfall 6: ConfigLoader fallback branch — three call sites, not two

**What goes wrong:** D-22 mentions "both fields" but `ConfigLoader.loadZonesConfig` has three string-to-type occurrences: `display.zones.$index.type` (line 103), `display.type` fallback (line 111), and `DisplayConfig.type` at line 25 in `loadConfig`. Missing any one leaves a `String` assignment to a `DisplayType` field.

**Why it happens:** The fallback zone construction at the bottom of `loadZonesConfig` reads `display.type` again — a third occurrence that is easy to miss.

**How to avoid:** After the enum change, the Kotlin compiler will flag all three as type errors, making them impossible to miss. Do not suppress warnings.

### Pitfall 7: WebhookService — extracting `executePost` changes the coroutine call stack for timeout

**What goes wrong:** `withTimeout(5_000)` is currently inside the `scope.launch {}` block in `send()`. If `executePost` is extracted as a `suspend fun`, care must be taken that the `withTimeout` wraps the `executePost` call, not that `executePost` itself contains `withTimeout` without the surrounding `scope.launch`.

**Why it happens:** D-18 says extract `executePost(url, payload)` that "contains the `withTimeout` + post call". If `executePost` is called from `scope.launch`, the timeout context is preserved correctly. The risk is accidentally placing `executePost` as a blocking call outside the launch scope.

**How to avoid:** Keep `scope.launch { executePost(url, payload) }` in `send()`. `executePost` is a `suspend fun` containing `withTimeout { ... }`.

### Example 2: validateAddZoneRequest in RequestValidators

```kotlin
// src/main/kotlin/com/anjo/validation/RequestValidators.kt
fun validateAddZoneRequest(req: AddZoneRequest): ValidationResult {
    val parts = req.ip.split(".")
    if (parts.size != 4) return ValidationResult.Invalid("IP must be a valid RFC1918 private address")
    val octets = try { parts.map { it.toInt() } } catch (_: NumberFormatException) {
        return ValidationResult.Invalid("IP must be a valid RFC1918 private address")
    }
    if (octets.any { it !in 0..255 }) return ValidationResult.Invalid("IP must be a valid RFC1918 private address")
    val valid = when {
        octets[0] == 10 -> true
        octets[0] == 172 && octets[1] in 16..31 -> true
        octets[0] == 192 && octets[1] == 168 -> true
        else -> false
    }
    return if (valid) ValidationResult.Valid else ValidationResult.Invalid("IP must be a valid RFC1918 private address")
}
```

Logic is identical to `IpValidation.isValidPrivateIpv4` — no new logic introduced. The existing three inline comments in `RequestValidators.kt` must be removed from the file during this edit.

### Example 3: Updated ZoneRoutes POST handler

```kotlin
// src/main/kotlin/com/anjo/routing/ZoneRoutes.kt
post("/") {
    val req = call.receive<AddZoneRequest>()
    if (zoneRegistry.containsIp(req.ip)) {
        return@post call.respond(HttpStatusCode.Conflict, "Zone with IP ${req.ip} is already registered")
    }
    val existing = zoneRepository.findById(req.ip)
    if (existing != null) {
        return@post call.respond(HttpStatusCode.Conflict, "Zone with IP ${req.ip} is already registered")
    }
    val zone = NetworkZone(
        id = req.ip,
        name = req.ip,
        ip = req.ip,
        type = DisplayType.MAX7219.name,
        discoveryMethod = "MANUAL",
        createdAt = Instant.now().toString(),
        lastSeenAt = null
    )
    zoneRepository.upsert(zone)
    zoneRegistry.addNetworkZone(zone)
    log.info("Manual zone added: ip=${req.ip}")
    call.respond(HttpStatusCode.Created, zone)
}
```

No IP validation logic inside the handler — the plugin handles it before the handler executes.
