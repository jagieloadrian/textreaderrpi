<gap_closure>
Closes 1 BLOCKER gap from 10-VERIFICATION.md:

- **SC-4** — "Webhook delivery status is visible in the history record for the corresponding display event." FAILED: `HistoryTable` has no webhook column, `HistoryRecord` has no webhook field, `HistoryRepository.insert()` does not persist it, and `SchedulerService.fire()` does not link the dispatch to the history insert performed by `ScreenDriverService.displayScheduled()`.

**Architectural decision (honest fire-and-forget per D-09):** `WebhookService.send()` is fire-and-forget and returns Unit (VERIFIED — must NOT change). We therefore record dispatch intent, not delivery confirmation:
- `"sent"` — a webhook URL resolved (per-schedule `webhookUrl` or global `defaultUrl`) and `send()` was invoked.
- `"skipped"` — no URL resolved (both null/blank, D-05), so no POST was attempted.
- `null` — IMMEDIATE display events (`POST /api/v1/text`); webhooks are scheduler-scoped only (D-03).

This is the only honest status a fire-and-forget design can guarantee. The status string is computed deterministically from URL resolution (independent of HTTP outcome), so it is known before `displayScheduled()` runs and can be written in the same history row as the display event.

Status is NOT updated after delivery (the coroutine outcome is logged via `log.warn` per D-15 but never written back), preserving D-09. This is documented in the SUMMARY as a deliberate scope boundary.
</gap_closure>
